# 3d_scene: сцены, рендер, калибровка и проверка результата

Проект создаёт параметрическую сцену «камера — стеклянная оболочка — шахматная
доска», рендерит её Mitsuba и передаёт изображения в `calibmar_cli`.
Исходная геометрия известна, поэтому можно сравнить найденный центр купола
с эталоном. Рабочая последовательность:

```text
scene.json + диапазоны из sweep.json
    → сцена каждого сочетания параметров
    → image.png + dome_position.json + calibmar_config.json
    → calibmar_cli
    → calibmar_result.json / .txt / .yaml + overlay.png
    → analysis/results.csv → Excel или Jupyter
```

Подробное руководство по панели и 3D-предпросмотру: [UI_GUIDE.md](UI_GUIDE.md).
Этот README — справочник по файлам, форматам и происхождению данных.

## С чего начать просмотр одного примера

Откройте папку кадра, например `renders/ИМЯ_НАБОРА/000001/`:

1. `image.png` — что увидела камера после рендера.
2. `dome_position.json` — **истинная геометрия**, известная из сцены.
3. `calibmar_config.json` — **что сообщили решателю**, включая начальный центр.
4. `calibmar_result/image.png/calibmar_result.txt` — краткий читаемый ответ.
5. `calibmar_result/image.png/calibmar_result.json` — полный машинный ответ.
6. `calibmar_result/image.png/overlay.png` — найденные узлы и проекции модели.

Для проверки центра сравнивайте:

```text
dome_position.json:
    dome_center_camera_opencv_m

calibmar_result/image.png/calibmar_result.json:
    housing_estimated.dome_center_camera_opencv_m
```

Оба вектора имеют вид `[X, Y, Z]`, единицы — **метры**, система OpenCV:
X вправо, Y вниз, Z вперёд относительно РЕАЛЬНОЙ камеры данного кадра.
Не сравнивайте этот ответ напрямую с мировыми координатами купола или
координатами относительно опорной камеры: это другие системы отсчёта.
В CSV разность уже рассчитана в столбцах `center_error_*`.

Старое имя эталонного файла — `ground_truth.json`. Новые экспорты пишут
`dome_position.json`; сборщик понимает оба имени и не дублирует строку,
если случайно найдены оба файла. Если есть оба, приоритет у нового.

## Запуск из консоли

В текущей установке общее окружение рендера находится в `/home/dfrolov/pixi.toml`,
окружение C++-решателя — отдельно в `../calibmar/.pixi/`.
Команды ниже с относительными путями выполняются из общего корня проекта.

Полный небольшой пример (диапазоны редактируются в начале скрипта):

```bash
bash 3d_scene/run_camera_sweep.sh
```

Диапазон имеет вид `от до шаг`. Переносы DX/DY/DZ заданы в метрах,
повороты RX/RY/RZ — в градусах; это люфт РЕАЛЬНОЙ камеры относительно
опорной. RX — крен, RY — тангаж, RZ — рыскание в принятой локальной системе.
Пример явного задания:

```bash
DX='0 0 0.01' DY='0 0.10 0.01' DZ='0 0 0.01' \
RX='0 0 1' RY='-10 10 2' RZ='0 10 2' \
SAMPLES=256 WIDTH=1920 UPSAMPLE=1 KEEP_UPSAMPLED=0 \
bash 3d_scene/run_camera_sweep.sh
```

Получится 11 × 6 × 11 = **726 кадров**. Перебор — полное декартово
произведение, а не выбор трёх значений из каждого диапазона. Если верхняя
граница не делится на шаг точно, последнее значение не превышает её.
`--prepare-only` сохраняет входные JSON и показывает число кадров без рендера.
Необязательный последний аргумент задаёт новую папку вывода.
Переменные `SOURCE_SCENE`, `BOARD_DISTANCE_M`, `VARIANT`, `PIXI_MANIFEST`
позволяют поменять исходную сцену, расстояние до доски и окружение.

Отдельные этапы:

```bash
# Один рендер; --sweep ПУТЬ добавляет полный перебор.
pixi run --manifest-path "$HOME/pixi.toml" python 3d_scene/scene_export.py \
  --scene 3d_scene/scene.json --out 3d_scene/renders/example \
  --width 1920 --samples 64 --variant cuda_ad_rgb --board-mode emissive

# Запуск CLI по готовым calibmar_config.json.
bash 3d_scene/run_calibmar.sh 3d_scene/renders/example

# Только сбор готовых чисел; ничего не рендерит и не калибрует.
python 3d_scene/collect_calibmar_results.py 3d_scene/renders/example
```

Bash-запускатель переходит в папку кадра, поэтому `images.directory="."`
в конфиге переносимо. Второй аргумент `run_calibmar.sh` — другой бинарник CLI.
Он автоматически подключает библиотеки стандартного окружения calibmar;
для другой установки задайте `LD_LIBRARY_PATH`.
`UPSAMPLE` задаёт увеличение картинки, `TIMEOUT_SEC` — лимит на один кадр
(по умолчанию 4 и 300). `KEEP_UPSAMPLED=0` удаляет дублирующую увеличенную
копию после обработки, сохраняя исходник, overlay и числовой ответ.
Повторный запуск CLI пересчитывает кадры и заменяет прежние файлы отчёта.

Не каждый запуск создаёт все перечисленные файлы. Один рендер без `--sweep`
не нуждается в manifest/experiment; панель не обязана создавать input_*;
при сбое CLI некоторые отчёты отсутствуют. Имя папки картинки сохраняет
расширение, чтобы frame.png и frame.jpg не смешивались.
Рядом с папкой ночного задания могут лежать `.sh`, `.log`, `.job.json`,
`.status`: команда запуска, общий журнал, PID/настройки и итоговый код.
`analysis/` также может содержать отдельные диагностические эксперименты;
их результаты не являются заменой основного отчёта.

## Что такое dome_position.json и кто его создаёт

Его пишет `scene_export.py` при экспорте, до запуска calibmar.
Функция `calibration_ground_truth()` обходит граф сцены, получает мировые
позы камеры и оболочки и вычисляет координаты центра через обратную
матрицу позы камеры. Это **эталон**, а не результат детекции или оптимизации.

| Поле | Смысл |
|---|---|
| `schema_version` | Версия структуры эталонного JSON |
| `length_unit` | Единица длины: m |
| `dome_center_world_m` | Центр в мировой системе сцены |
| `dome_center_camera_native_m` | Центр в исходных осях камеры: X вперёд, Y влево, Z вверх |
| `dome_center_camera_opencv_m` | Тот же центр в осях OpenCV: X вправо, Y вниз, Z вперёд |
| `T_world_from_camera_native` | Перевод точки из исходной системы камеры в мир |
| `T_camera_native_from_world` | Обратное преобразование |
| `T_camera_opencv_from_world` | Перевод мировой точки в систему OpenCV камеры |
| `T_camera_opencv_from_dome` | Перевод из системы купола в систему OpenCV камеры |
| `dome_inner_radius_m`, `dome_outer_radius_m` | Радиусы внутренней и внешней поверхности |
| `dome_thickness_m`, `glass_ior` | Толщина и показатель преломления стекла |
| `K_opencv` | Идеальная матрица камеры ДО преломления стеклом |
| `image_resolution_px`, `image_file` | Размер и имя исходного изображения |
| `sphere_orientation_observable` | false: у идеальной сферы нельзя восстановить собственный поворот по её форме |

Матрицы действуют на столбцы: `T_destination_from_source @ point_source`.
K не включает купол и не является самостоятельным способом проектирования
мировых точек через стекло.

## Что решатель знает из calibmar_config.json

```json
"housing": {
  "interface": "DOMEPORT",
  "inner_radius_m": 5.95,
  "layers": [{"thickness_m": 0.05, "refractive_index": 1.52}],
  "inside_refractive_index": 1.0,
  "outside_refractive_index": 1.0
},
"initialization": {
  "dome_center_camera_opencv_m": [0.0, 4.17193, -4.17193],
  "estimate_dome_offset": false
}
```

Это фрагмент конфигурации, не весь JSON. Ещё заданы камера, размер кадра,
число клеток/шаг доски, путь к картинке и настройки детекции.
Начальный центр — положение относительно ОПОРНОЙ камеры без неизвестного
люфта реальной камеры. Он только начальное приближение и оптимизируется.
При `estimate_dome_offset=true` CLI заменяет этот старт собственной оценкой.
Сам CLI по-прежнему допускает старые массивы initial_params; новые экспорты
используют именованные поля.

В текущем расчёте подбираются центр и поза доски. Камера, радиус, толщина и
показатели преломления фиксированы. Список layers описывает порядок изнутри
наружу, но пока реализован **один слой** (две поверхности); несколько слоёв
CLI явно отклоняет. Рендерер сейчас использует одинаковую среду внутри и снаружи.

## JSON, TXT и YAML: куда смотреть

- **TXT** — читаемая сводка успешного кадра: `DomeCenterX_m/Y_m/Z_m`, стекло,
  начальное приближение, параметры камеры, RMSE и максимальное отклонение.
  Для быстрого просмотра чисел начните с него.
- **JSON** — полный ответ CLI: те же оценки плюс координаты каждого узла,
  неопределённости, ковариация, поза доски, входной конфиг и настройки запуска.
  Его читает сборщик CSV. Он также содержит сведения о неуспехе.
- **YAML** — совместимый с исходным calibmar формат обмена/повторного импорта.
  Там сохранены его модель и упорядоченные массивы; полных диагностических
  полей CLI и всех узлов в нём нет. Это не другой расчёт.

`Cx/Cy/Cz` в прежних housing-отчётах — обозначения центра, принятые в calibmar.
Они не равны `cx/cy` главной точки камеры. Новая TXT-сводка различает
`DomeCenterX_m` и `CameraPrincipalPointX_px`, включая разные единицы.

JSON отчёта версии 2 использует:

| Поле | Содержание |
|---|---|
| `status`, `message` | Успех/причина неуспеха |
| `housing_initial` | Именованное начальное приближение купола |
| `housing_estimated` | Именованный найденный купол, включая `dome_center_camera_opencv_m` |
| `housing_std_deviations` | Оценённые стандартные отклонения с такими же физическими именами; нули у фиксированных параметров |
| `input_config` | Конфиг, фактически прочитанный при запуске; у старых входов здесь могут остаться legacy-массивы |
| `invocation`, `effective_settings` | Команда, рабочая папка и применённые настройки |
| `camera_params_input` | Исходные параметры модели камеры; для PINHOLE: fx,fy,cx,cy, пиксели COLMAP |
| `rmse_px`, `rmse_all_points_px` | sqrt(mean(dx²+dy²)) по всем обнаруженным узлам |
| `rmse_inliers_px`, `fit_rmse_px` | Ошибка принятых наблюдений кадра и всего расчёта |
| `max_error_px`, `max_error_point_index` | Максимальное евклидово отклонение и индекс узла с нуля |
| `num_points`, `num_rejected` | Число узлов и отвергнутых наблюдений |
| `board_to_camera` | Найденная поза доски: кватернион w,x,y,z и перенос в метрах |
| `points` | detected_px, projected_px, residual_px и error_px для каждого узла |
| `full_covariance` | Матрица ковариации в одном массиве, по строкам |
| `covariance_num_params`, `covariance_parameter_names` | Размер матрицы и подписи строк/столбцов в том же порядке |

В housing-объектах именованы центр, `inner_radius_m`, `layers` (толщина и
преломление), среды inside/outside. Числового `housing_estimated_params`
в новом отчёте нет. Сборщик поддерживает и старые отчёты.
Стандартное отклонение из локальной ковариации не включает неопределённость
фиксированных входов и не гарантирует отсутствие другого решения задачи.

## Картинки и ошибки

`overlay.png` — исходник (возможно увеличенный) с зелёными окружностями
обнаруженных углов и красными проекциями найденной модели.
`image_upsampled.png` — та же увеличенная картинка без отметок, новых данных
в ней нет. Исходный `image.png` лежит в папке кадра.

Все ошибки JSON/CSV измеряются в пикселях ИСХОДНИКА, даже если overlay увеличен
в 4 раза. Тогда расстояние в пикселях файла overlay будет в 4 раза больше.
RMSE — усреднение, не верхняя граница; max_error_px — максимум.
Ни одна из этих метрик не является ошибкой детекции относительно идеальных
узлов: эталонные пиксельные проекции узлов отдельно не вычисляются.
Малая ошибка не доказывает правильный центр или физическую допустимость
модели. Статус OK сообщает о выполнении расчёта, не о доказанной истинности.

## Таблица CSV

Одна строка на папку с dome_position.json (или legacy ground_truth.json).
`param.*` — параметры сцены, `render.*` — seed/сэмплы/вариант/режим доски.
`center_true_*` и `center_estimated_*` — эталон и оценка в метрах OpenCV;
`center_error_*` — найденное минус истинное; `center_error_norm_m` — длина
этого вектора. Пути к подробностям: result_json и overlay_png.

Неуспехи сохраняются отдельными строками, недостающие метрики пустые, не нули.
Код процесса находится в exit_code.txt (124 — timeout); конкретная причина
детекции/расчёта — в JSON и журнале. CSV: UTF-8 с BOM, `;`, десятичная точка.
Для запятой есть `--delimiter ','`; другое место вывода — `--csv ПУТЬ`.

## Версии и хеши: что именно они подтверждают

`exporter_version` — **поле**, не отдельный файл. Это вручную заданная версия
кода/протокола экспортёра (`EXPORTER_VERSION` в scene_export.py), записывается
в experiment.json и render_info.json. Это не версия Mitsuba и не контрольная
сумма программы. Начиная с 1.6 используется новое имя эталона. Старые рендеры
сохраняют свою исходную версию 1.5 даже после косметической миграции отчётов.
Версия Mitsuba отдельно записана в `mitsuba_version`.

`schema_version` — версия структуры конкретного JSON, независимая от версии
экспортёра. Версия JSON отчёта CLI теперь 2, эталонного файла пока 1.

Хеш вычисляет `scene_model.fingerprint()` буквально так:

```python
hashlib.sha256(
    json.dumps(value, sort_keys=True, allow_nan=False).encode()
).hexdigest()
```

Это SHA-256 JSON-ОБЪЕКТА после сериализации Python, не SHA-256 исходных байтов
файла. Используются стандартные пробелы/ASCII-экранирование json.dumps и UTF-8.
Порядок ключей нормализован; порядок массивов, числа 1 и 1.0, значения строк
и все поля объекта значимы. Простое изменение отступов файла не меняет хеш.

| Где | Что хешируется |
|---|---|
| `experiment.json: scene_hash` | Весь объект source_scene.json — базовая сцена с применёнными CLI-настройками рендера |
| `experiment.json: sweep_hash` | Весь объект sweep.json — ranges, min/max/step, enabled и другие присутствующие поля |
| `render_info.json: scene_hash` | Весь scene.json конкретного кадра после применения сочетания параметров |
| `manifest.jsonl: scene_hash` у complete | Тот же объект сцены конкретного кадра |

В сцену входят граф/преобразования объектов, камера/сенсор, материалы,
геометрия, параметры, настройки рендера (seed, сэмплы и т.д.), units,
conventions, description, preview и другие присутствующие поля. Специального
отбора «только влияющих на оптику» нет. Даже изменение описания/предпросмотра
может изменить хеш, не изменяя физического изображения.

Проверка из общего корня:

```bash
python - /путь/к/набору <<'PY'
import hashlib, json, sys
from pathlib import Path
root = Path(sys.argv[1])
def load(p): return json.loads(p.read_text(encoding='utf-8'))
def digest(v): return hashlib.sha256(json.dumps(v, sort_keys=True, allow_nan=False).encode()).hexdigest()
e = load(root/'experiment.json')
print('Base scene:', digest(load(root/'source_scene.json')) == e['scene_hash'])
print('Sweep:', digest(load(root/'sweep.json')) == e['sweep_hash'])
for p in sorted(root.glob('*/render_info.json')):
    print(p.parent.name, digest(load(p.parent/'scene.json')) == load(p)['scene_hash'])
PY
```

Эти хеши помогают обнаружить изменение описаний и не смешивать эксперименты
при продолжении рендера. Они **не хешируют image.png, JSON ответа, XML,
текстуру или бинарник решателя** и не доказывают правильность расчёта.
Для строгой проверки целостности результатов нужны отдельные контрольные
суммы самих файлов. В старых диагностических run.json мог быть хеш бинарника;
текущий простой Bash-запускатель его не вычисляет.

## Что такое manifest.jsonl

JSONL означает «один самостоятельный JSON-объект на строку». Это журнал
событий, не один большой JSON-массив. На кадр обычно записываются как минимум
две строки: running перед началом и complete после сохранения результата.
При ошибке пишется failed с причиной. При повторе могут появиться новые строки
того же кадра; актуальна последняя запись для его index.

Поля: index (номер), parameters (сочетание параметров), directory (папка),
time_utc (время UTC), status; у complete добавляется scene_hash, у failed — error.
Журнал помогает продолжить рендер, пропустить завершённые случаи и сохранить
причину ошибки. Прерванная последняя строка при чтении пропускается.
Значение `complete` относится к **рендеру**, не к успешности calibmar.
Калибровка отдельно отражается в exit_code.txt и results.csv.

`.render.lock` защищает набор от двух писателей; существование самого файла
не означает активный процесс — блокировкой управляет операционная система.
experiment.json предотвращает продолжение с другой базой/диапазонами/версией
экспортёра. Старый набор версии 1.5 после изменения экспортёра может не
продолжиться версией 1.6; не подменяйте версию/хеши ради обхода проверки.
