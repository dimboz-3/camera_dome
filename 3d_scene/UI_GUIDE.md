Параметрическая сцена: JSON → OCP Viewer и Mitsuba

Запуск из корня проекта. Сначала в отдельном терминале запустите `pixi run python -m ocp_viewer` и откройте http://localhost:3939. Затем:

```bash
bash 3d_scene/open_panel.sh
```

Из другого каталога: `bash /home/di/3d_scene/open_panel.sh`.
Для установки окружения используется `pixi install`; Mitsuba и отдельный OCP Viewer включены в pixi.toml.
Tk закреплён на сборке `xft_*`, чтобы текст и символы галочек отображались корректно.

Как пользоваться панелью

1. Параметры сгруппированы в таблице `ttk.Treeview` с сеткой строк и столбцов: опорная камера, шаблон,
   стекло и люфт реальной камеры. Двойной щелчок по «Текущее», «От», «До»,
   «Шаг» открывает числовой ввод; Enter или выход из ячейки подтверждает,
   Escape отменяет. Можно выбрать строку и использовать общий ползунок
   под таблицей либо точное поле с кнопкой «Применить».
   Галочка в колонке «Перебор» (или пробел на выбранной строке) включает
   диапазон. Без галочки параметр фиксируется на текущем значении;
   введённый диапазон сохраняется. Счётчик сразу учитывает галочки.
   «Применить диапазоны» проверяет границы; «Сохранить настройки» пишет JSON.
   Текущее значение может лежать вне диапазона. Расстояния показаны в см.
2. Выберите направление камеры и отображение оболочки: поверхность,
   рёбра или скрытая. Галочка «Сегмент оболочки» показывает угловой участок
   вместо полной оболочки; по умолчанию его угловой диаметр 20°.
   Эти настройки не меняют геометрию Mitsuba и STEP.
3. «Сохранить настройки» записывает текущую сцену в scene.json, а диапазоны
   в sweep.json. «Перечитать JSON» загружает внешние изменения этих файлов.
4. «Экспорт JSON / XML» сохраняет только текущую сцену, без рендера.
5. «Рендерить текущую» считает один кадр; «Рендерить набор» — полное
   декартово произведение включённых диапазонов, с текущими значениями
   остальных параметров. Число комбинаций видно рядом с кнопками.
6. «Стоп» прерывает текущий процесс рендера; уже готовые кадры сохраняются.
   «Продолжить…» принимает папку эксперимента и пропускает готовые кадры.
   При ошибке одного кадра перебор продолжится, ошибка попадёт в manifest.jsonl.

Автоматическое восстановление рабочего набора

Текущие значения всех параметров, диапазоны и флаги «Перебор» автоматически
сохраняются в `3d_scene/panel_state.json` после подтверждения ввода или
переключения галочки (задержка 400 мс). При закрытии панели изменения
дописываются сразу. Также восстанавливаются направление камеры, вид
оболочки, показ вариантов, размер пирамид, лимит просмотра, настройки
рендера и закрепление окна поверх остальных.
При следующем запуске этот рабочий набор имеет приоритет над scene.json
и sweep.json. «Перечитать JSON» возвращает настройки из этих двух файлов;
«Сохранить настройки» явно записывает рабочий набор и в них. Автосохранение
использует отдельный локальный файл, исключённый из Git. Незавершённый
или некорректный ввод не затирает последний успешно сохранённый набор.

Размер шрифта

Сверху окна «Размер шрифта, пт» меняет размер текста всей панели (8–24 пункта).
Изменение стрелками применяется сразу; введённое число — по Enter, выходу
из поля или кнопке «Применить». Высота строк и ширина колонок подстраиваются.
При большом размере доступна горизонтальная прокрутка таблицы.
Настройка автоматически сохраняется в локальный `3d_scene/ui_settings.json`
и восстанавливается при следующем запуске. Этот файл исключён из Git;
размер шрифта не изменяет сцену, параметры эксперимента и рендер.
Колонки имеют ширину по заголовкам и значениям с небольшим запасом,
без растяжения на всё окно. Текущие значения выделены полужирным шрифтом.
При вводе более длинного числа колонка расширяется. Границы можно двигать мышью.

Светящаяся доска

В блоке Mitsuba поле «Доска» переключает «Обычная» (`board_mode="diffuse"`)
и «Светящаяся» (`board_mode="emissive"`). Выбор сохраняется автоматически.
По умолчанию остаётся обычная доска, чтобы прежняя модель освещения
сохранялась до явного переключения.

В светящемся режиме шахматная текстура задаёт излучение area emitter,
отражательная способность доски равна нулю, внешняя студийная лампа
не создаётся, а фон определяется `background_radiance` (по умолчанию 0).
Излучающая сторона направляется к реальной камере. Геометрия, UV,
координаты клеток и ground truth не меняются. Белые и чёрные клетки
используют значения `materials.board_surface.white` и `black` как линейную
яркость (после квантования существующей 8-битной текстуры).

Это модель экрана/подсвеченного шаблона, полезная для геометрической
калибровки. Она убирает шум от выборки внешней лампы, но сохраняет
преломление, отражения и статистический шум стекла. Полностью устранить
зернистость одним переключателем нельзя: число сэмплов остаётся важным.
Рендер из терминала: добавьте `--board-mode emissive` к обычной команде.
В каждом render_info.json режим записывается как `board_mode`.

Рендер на GPU и шум

В блоке Mitsuba «Вычисления» выбирает CPU, CPU (LLVM) или GPU NVIDIA (CUDA).
Выбор сохраняется автоматически. CUDA использует wavefront (отключены
SymbolicLoops и SymbolicCalls), что обходит ошибку OptiX `copysign.f32`
на проверенном драйвере NVIDIA 535.309.01 с RTX 3060. Проходы автоматически
делятся по бюджету `render.gpu_max_rays_per_pass` (по умолчанию 4 млн путей),
чтобы ограничивать пиковую видеопамять. Даже при бюджете меньше разрешения
минимальный проход содержит один сэмпл на пиксель. Результаты усредняются
с весами по числу сэмплов; число проходов и seeds записываются в render_info.
Первый GPU-запуск может быть медленнее из-за компиляции ядер.

Пример из терминала:

```bash
pixi run python 3d_scene/scene_export.py \
  --scene 3d_scene/scene.json --out /tmp/dome-gpu \
  --variant cuda_ad_rgb --width 640 --samples 256
```

При 4 сэмплах на пиксель стекло и прямоугольный источник дают сильный
шум и одиночные яркие точки. Для сравнения используйте 256 сэмплов,
для более чистых кадров — 1024 и выше. GPU ускоряет набор сэмплов,
но само по себе переключение backend не устраняет шум. Для геометрических
тестов яркие точки не подавляются фильтром и значения не ограничиваются
во время интегрирования. Ограничение до [0,1] выполняется только при PNG.
Источники задаются явным нейтральным RGB, чтобы равномерный спектр
не давал красноватый оттенок при преобразовании в sRGB.

Центр вращения Viewer по умолчанию — оптический центр текущей реальной
камеры, включая люфт и преобразования родительских групп. При её перемещении
центр следует за камерой. Если позиция не меняется, ручное панорамирование
и выбранный вид сохраняются. Это относится и к показу множества вариантов:
опорой остаётся текущая реальная камера.

Множество вариантов в одном просмотре

- «Показать варианты перебора» накладывает варианты на текущую сцену.
  Колонка «ППП» задаёт показ отдельно для каждого параметра:
  «ППП — полный перебор параметра при визуализации».
  Без галочки берутся первое и последнее допустимые значения диапазона;
  с галочкой — все его значения. Текущая сцена добавляется всегда.
  Например, 5 сдвигов с ППП и 5 углов без ППП дают 5×2=10 сочетаний
  вместо 25. Лимит предпросмотра сохраняется.
  Флаг «Перебор» определяет участие в расчёте; ППП влияет только на
  визуализацию. Если «Перебор» выключен, используется текущее значение
  независимо от ППП. Флаги ППП сохраняются в диапазонах как `preview_full`.
  Старый общий флаг переносится на строки, в которых ещё нет своего ППП.
  Текущая камера остаётся яркой с полной пирамидой, дополнительные камеры
  показаны приглушёнными пирамидами FOV в масштабе ×0,5. Глубина, ширина
  и высота уменьшаются вдвое, углы поля зрения сохраняются. Галочка
  «Пирамиды вариантов ×1» возвращает размер как у текущей камеры.
- Совпадающие экземпляры каждого объекта объединяются по id, мировой
  матрице, геометрии и видимым свойствам. Точность сравнения матриц — 1e-8.
  Перебор IOR не создаёт копий в CAD; в Mitsuba кадры остаются разными.
  Неподвижные шаблон и оболочка показываются один раз. Изменившиеся
  шаблоны показаны контурами с диагоналями, текущий — клетками.
- Лимит предпросмотра — от 1 до 500 вариантов (по умолчанию 100).
  При превышении выбираются равномерные индексы в декартовом произведении,
  включая крайние при лимите >1. Всё произведение при этом не создаётся.
  Такая выборка не гарантирует покрытия каждой оси. Статус показывает
  выбранное и полное количество. Текущая сцена добавляется независимо от
  выборки; совпадающие объекты объединяются и с ней.
- «Сегмент оболочки» сохраняет центр участка в направлении от центра
  оболочки к текущей опорной камере, в том числе при наложении вариантов.
  Люфт реальной камеры не двигает сегмент. Для широкого диапазона поз можно
  увеличить угол, выключить сегмент либо выбрать «Рёбра» или «Скрыть».
- Лимит и показ вариантов влияют только на предпросмотр. JSON/XML, STEP и
  одиночный рендер экспортируют текущую сцену; пакетный рендер считает весь
  включённый перебор, каждую сцену отдельно.

Рендер идёт отдельным процессом; просмотр можно продолжать. Поля ширины и
числа сэмплов относятся к следующему запуску. Ширина по умолчанию 640 px,
64 сэмпла; высота сохраняет исходное соотношение сторон. Исходная камера
имеет 1920×1536 px, f=1200 px; уменьшение рендера сохраняет поле зрения.
IOR влияет на Mitsuba, а в CAD меняется только геометрия.

Панель закреплена поверх окон; галочка снимает закрепление. Если панель
свернулась — Alt+Tab. Закрытие останавливает управление и активный рендер,
сцена остаётся в OCP. Для возвращения управления запустите команду снова.

Определения параметров

- pitch_deg — угол радиус-вектора камеры над плоскостью XY.
- yaw_deg — азимут радиус-вектора вокруг мировой Z.
- roll_deg — крен вокруг локальной оптической оси камеры +X.
- board_distance_m — смещение центра доски вдоль локальной +X опорной камеры.
- thickness_m — толщина оболочки. Внешний радиус фиксирован, камера следует
  за внутренней поверхностью, сохраняя зазор camera_clearance_m.
- ior — показатель преломления стекла; с обеих сторон оболочки — воздух.

Направление камеры выбирается явно:

- «Вдоль +X, рыскание вокруг Z» сохраняет исходную SCAD-компоновку:
  камера смотрит вдоль +X, повёрнутого на текущий yaw. Pitch меняет
  положение, но не наклон оптической оси.
- «Вдоль радиуса наружу» направляет оптическую ось по радиус-вектору.
- «На центр доски» направляет камеру на текущий центр доски.

Во всех режимах roll задаёт крен вокруг оптической оси. Доска следует за номинальной позой опорной камеры. При изменении pitch/thickness
перемещается опорная точка. Оранжевый маркер и короткие оси обозначают опорную
камеру, красный маркер и пирамида — реальную.

Группа «Реальная камера — люфт» задаёт параметры `camera_dx_m`, `camera_dy_m`,
`camera_dz_m`, `camera_rx_deg`, `camera_ry_deg`, `camera_rz_deg`. При разрешении
сцены они также сохраняются в `parameterization.camera_offset`. Если новые
ключи присутствуют в `parameters`, они имеют приоритет над этим полем:
`translation_m` — перенос в локальных осях опорной камеры, `rotation_deg` —
добавочный поворот Rz @ Ry @ Rx после номинального поворота. В интерфейсе
переносы показаны в сантиметрах, углы — в градусах. Люфт не меняет положение
шаблона и опорной точки. Сохранение, одиночный и пакетный рендер используют
эти же значения. Люфт участвует в переборе наравне с номинальной установкой.

Изменение относительно прежнего поведения: yaw/roll опорной камеры теперь
двигают и ориентируют шаблон вместе с установкой. Для отклонения только
реальной камеры используйте поля люфта. Режим «На центр доски» при такой
привязке совпадает с номинальным направлением +X до добавления люфта.

Viewer при каждом обновлении получает нейтральные плоскости отсечения,
чтобы оставшиеся настройки вкладки Clip не разрезали модель повторно.
В `scene_cad.shell_geometry()` строится полная оболочка как разность сфер.
В `scene_preview.section_geometry()` только для просмотра она пересекается
с конусом (`&`). Вершина конуса совпадает с центром оболочки, его ось
направлена к опорной камере. Угловой диаметр 20° означает полуугол 10°:
граница участка круглая, боковые поверхности направлены к центру сферы.
Поле «Угловой диаметр, °» принимает 1–170° и сохраняется автоматически
вместе с галочкой как `preview.section_angle_deg` и `preview.shell_segment`.
Отсечение работает и с отображением рёбер. Прежнее `section_radius_m`
больше не задаёт размер выреза; старые сцены с режимом `section` открываются
как сегмент 20°. Полные сферы в CAD/STEP и Mitsuba сохраняются.
Для устойчивой триангуляции вырез сначала строится у полюса +Z, затем
готовый сегмент поворачивается к опорной камере. Боковой вырез из исходной
сферы давал длинные хорды и зубцы при графическом сечении тонкой оболочки.

Источники данных

- scene.json — геометрия, вложенный граф, материалы, параметры установки и люфта,
  правила их применения, настройки рендера и просмотра.
- sweep.json — диапазоны, `enabled` и текущее `value` для фиксированных
  параметров. CLI использует текущее значение из исходной сцены. Старые
  файлы без `enabled` сохраняют включённые диапазоны; отсутствующие
  диапазоны люфта фиксируются на текущем люфте. Если верхняя граница не попадает на шаг,
  используется последняя точка, не превосходящая её.
- board_27_19.scad — прежний источник; начальная JSON-сцена перенесена из него
  с переводом сантиметров в метры. Теперь сцена управляется JSON, изменения
  SCAD автоматически не подхватываются.

Единицы JSON: метры и градусы. Каждый узел имеет id, type,
transform.translation_m, transform.rotation_deg; любой узел может иметь children.
Поле conventions явно фиксирует оси, порядок матриц и ориентацию доски;
старые файлы без этого поля используют те же соглашения версии 1.
Повороты как в OpenSCAD: Rz @ Ry @ Rx; локальная матрица T @ R;
мировая — M_parent @ M_local.

Преобразования углов и матриц выполняет `scipy.spatial.transform.Rotation`:
`from_euler('xyz', angles, degrees=True).as_matrix()` и обратное
`from_matrix(matrix).as_euler('xyz', degrees=True)`. Строчные `xyz` означают
повороты вокруг неподвижных осей X, Y, Z в таком порядке. При Y = ±90°
углы неоднозначны: SciPy предупреждает и выбирает Z = 0; ориентация сохраняется.
Корневые группы можно вкладывать и
перемещать/вращать целиком, оба экспортёра обходят одну и ту же иерархию.
Параметризованные shell, camera и board_reference находятся в системе rig;
центр оболочки совпадает с началом rig. Параметры пересчитывают эти узлы;
для переноса всей установки меняйте transform группы rig или её предка.

Сохранённый scene.json каждого кадра содержит уже вычисленные переносы,
повороты, геометрию и материалы. Он имеет resolved=true и при прямом
рендере читается как есть — без повторного вычисления параметризации.
Повторное открытие такого файла в редакторе применит правила параметров.

Файлы рендера

```text
renders/batch_.../
  experiment.json          # контроль соответствия при продолжении
  source_scene.json        # исходная сцена эксперимента
  sweep.json
  manifest.jsonl           # параметры, номер и статус каждого кадра
  000001/
    scene.json             # самостоятельная, полностью вычисленная сцена
    scene.xml              # Mitsuba, аналитическая оболочка из двух границ
    board_texture.png      # точные 27×19 клеток; nearest-фильтрация
    image.png              # полный размер, RGB sRGB 8 бит
    dome_position.json      # эталонный центр купола в системе камеры и преобразования
    render_info.json       # версия Mitsuba, backend, seed, время, настройки
```

Красный шарик радиусом 1 см, пирамида и оси в рендер не попадают. Участок
оболочки существует только в CAD-просмотре. В Mitsuba всегда две полные
аналитические сферы — внешняя R и внутренняя R−t с обратной нормалью.
Стекло гладкое, без поглощения; доска диффузная. По умолчанию
`render.lighting_mode="studio"`: окружение чёрное (`background_radiance=0`),
а доску освещает отдельный прямоугольный источник сверху со стороны камеры
(`key_light_radiance=12`). Его положение выводится из мировой позы доски,
поэтому перенос всей установки не ломает освещение. Источник и его отражения
могут давать блики. Старое равномерное окружение доступно через
`lighting_mode="environment"` и `environment_radiance`.

Результат рендера сохраняется только в `image.png`, в полном разрешении,
в sRGB с 8 битами на канал и ограничением яркости до [0,1]. EXR и дублирующий
preview.png больше не создаются. Старые результаты автоматически не удаляются.

Для каждого кадра (также при экспорте без рендера) записывается
`dome_position.json`. В нём:

- `dome_center_world_m` — центр купола в мировой системе;
- `dome_center_camera_native_m` — центр в системе реальной камеры:
  X вперёд, Y влево, Z вверх;
- `dome_center_camera_opencv_m` — центр в системе OpenCV:
  X вправо, Y вниз, Z вперёд;
- матрицы `T_destination_from_source`, действующие на векторы-столбцы;
- наружный и внутренний радиусы, толщина, IOR, разрешение и `K_opencv`.

Центр вычисляется как `inverse(T_world_from_camera) @ center_world`,
по полным мировым матрицам, с учётом люфта камеры и всех родительских групп.
В OpenCV-системе он может иметь отрицательную Z: купол окружает камеру,
его центр не обязан находиться перед ней. `K_opencv` относится к идеальной
камере до преломления, а не является моделью всей системы камера–купол.
Пиксельные координаты: центр верхнего левого пикселя (0,0), поэтому
cx=(width−1)/2, cy=(height−1)/2. Проверка первичных лучей Mitsuba подтверждает
это соглашение. Для сферической оболочки пространственный поворот
не наблюдаем: для калибровки существенны положение центра и радиусы.

Версия экспортёра 1.5 добавляет режим светящейся доски. Старые эксперименты
версий 1.1–1.4 следует оставить как есть; новые запускайте в новой папке,
чтобы не смешивать результаты при продолжении.

Рендер из командной строки

```bash
# Сохранённый кадр — без изменения его явного графа:
```

Объектная модель и build123d

`Object3D.local_matrix()`, `world_matrix()` и `walk()` вычисляют позы и обходят
дерево. Свободных `matrix44_local` и `walk_graph` больше нет. `walk()` возвращает
пары `(Object3D, мировая_матрица)`; исходные поля узла доступны через `.data`.
`Scene.from_dict(document)` и `Scene.load(path)` загружают документ без
пересчёта параметров. `to_dict()` и `save(path)` сохраняют полное дерево,
материалы, единицы и соглашения. `resolve_scene()` нужен для применения
параметров эксперимента; для восстановления готового графа он не требуется.

`Scene.to_build123d()` возвращает `Compound`: группы остаются группами,
локальные переносы и повороты применяются на каждом уровне, включая корень.
Метры из JSON переводятся в миллиметры build123d/STEP. Оболочка — полное
аналитическое тело, доска — плоские грани клеток без добавленной толщины,
камера — справочный каркас поля зрения. Визуальный срез оболочки существует
только в предпросмотре и не меняет CAD-сборку или рендер Mitsuba.

Кнопка «Экспорт STEP» сохраняет `scene.step` и `scene.scene.json` в новой папке
`renders/cad_...`. STEP хранит геометрию, имена, иерархию и цвета; показатели
преломления, разрешение камеры и прочие параметры сохраняются в соседнем JSON.
Экспорт из командной строки (из корня camera_dome):

```sh
.pixi/envs/default/bin/python 3d_scene/scene_export.py \
  --scene 3d_scene/scene.json --out /tmp/scene-export \
  --export-only --step /tmp/scene-export/scene.step
```

Для Python:

```python
from scene_model import Scene, read_json, resolve_scene

scene = Scene.from_dict(resolve_scene(read_json("3d_scene/scene.json")))
assembly = scene.to_build123d()
scene.export_step("/tmp/scene.step")
```

Поля `sensor.near_clip_m` и `sensor.far_clip_m` явно задают плоскости отсечения
Mitsuba. Для старых документов они добавляются при сохранении со значениями
0.00001 м и 10000 м. `units` проверяется при загрузке: версия 1 принимает метры
и градусы, другой набор единиц требует предварительного пересчёта.

Пакетная калибровка и таблица для анализа

Экспортёр сохраняет calibmar_config.json рядом со scene.json, dome_position.json
и image.png. В конфиге images.directory=".": папку кадра можно переносить.
При продолжении старого набора экспортёр добавляет недостающий конфиг к уже
готовым кадрам без повторного рендера. Настройки детекции/решателя при
необходимости можно менять непосредственно в calibmar_config.json.

1. Запуск CLI из корня общего проекта:

```bash
bash 3d_scene/run_calibmar.sh /путь/к/набору
```

Bash-скрипт находит calibmar_config.json и для каждого запускает CLI из папки
кадра. Никакого разбора JSON, генерации конфигов или вычисления ошибок в нём нет.
Другой бинарник можно передать вторым аргументом. Стандартные библиотеки из
calibmar/.pixi/envs/default/lib подключаются автоматически. Если окружения нет:

```bash
pixi install --manifest-path calibmar/pixi.toml --locked
```

Для нестандартных библиотек задайте LD_LIBRARY_PATH. Число увеличения картинки
и лимит времени задаются переменными окружения (по умолчанию 4 и 300 секунд):

```bash
UPSAMPLE=4 TIMEOUT_SEC=300 bash 3d_scene/run_calibmar.sh /путь/к/набору /путь/calibmar_cli
```

Результаты каждого случая:

```text
000001/
  calibmar_config.json
  scene.json
  dome_position.json
  image.png
  calibmar_result/
    calibmar.log
    exit_code.txt
    image.png/
      calibmar_result.json
      calibmar_result.yaml
      calibmar_result.txt
      image_upsampled.png
      overlay.png
```

exit_code.txt хранит RUNNING во время работы, затем код завершения процесса
(0 — успех, 124 — превышение времени). При сбое подробности находятся в журнале.
Следующие случаи всё равно обрабатываются. Повторный запуск пересчитывает
кадры и удаляет известные файлы предыдущих ответов, чтобы не принять старый
успех за новый результат. Старый run_calibmar.py заменён Bash-скриптом.

В overlay зелёные окружности — обнаруженные узлы, красные — проекции модели.
JSON содержит detected_px и projected_px с субпиксельными координатами.
Увеличение относится только к просмотру; детекция идёт на исходном разрешении.

2. Сбор готовых результатов в таблицу:

```bash
python 3d_scene/collect_calibmar_results.py /путь/к/набору
```

Сборщик не запускает CLI. Он читает папки с dome_position.json и готовые ответы,
пишет ПАПКА_НАБОРА/analysis/results.csv. Другое место: --csv /путь/results.csv.
CSV — UTF-8 с BOM, разделитель ;, десятичная точка; для запятой: --delimiter ','.
Для Excel при необходимости задайте разделитель и десятичную точку при импорте.
Оба скрипта не используют manifest: папки без нужного для них файла не находятся.

Основные столбцы: case_id, status, message; param.* (метры/градусы), render.*;
rmse_px, rmse_all_points_px, rmse_inliers_px; max_error_px (максимальное
отклонение по всем узлам в пикселях исходника), max_error_point_index (индекс
узла с нуля); center_true_{x,y,z}_m,
center_estimated_{x,y,z}_m; center_error_{x,y,z}_m (найденное минус эталон),
center_error_norm_m (длина вектора ошибки); result_json, overlay_png.
Отсутствующие метрики остаются пустыми. NOT_PROCESSED — нет ответа;
CLI_ERROR — неуспешный запуск, подробности в calibmar.log. Сборщик также
понимает старые результаты Python-обёртки. Код возврата 1 означает наличие сбоев.

Один кадр — одна независимая калибровка. Радиус, толщина, показатели преломления
и камера фиксированы; подбираются центр купола и поза доски. Эталонный центр
в начальное приближение не передаётся. Главная точка переводится из OpenCV
в COLMAP добавлением 0,5 пикселя. Ошибки центра — в метрах, OpenCV:
X вправо, Y вниз, Z вперёд. RMSE — согласие модели с найденными узлами
в пикселях исходника, не ошибка относительно идеальных проекций.
Статус OK не доказывает правильность геометрии. CSV можно изучать в Excel/Jupyter.

Готовый консольный перебор реальной камеры

```bash
bash 3d_scene/run_camera_sweep.sh
```

В начале run_camera_sweep.sh задаются DX, DY, DZ (метры), RX, RY, RZ
(градусы). Каждая строка — «от до шаг»; одинаковые границы фиксируют параметр.
Это смещение и поворот реальной камеры относительно опорной, не её
pitch/yaw/roll. Можно передавать значения без редактирования файла:

```bash
DX='-0.01 0.01 0.01' RY='-2 2 2' bash 3d_scene/run_camera_sweep.sh
```

По умолчанию 9 комбинаций, расстояние до доски 1 м, 1920×1536, 64 сэмпла,
CUDA и светящаяся доска. Скрипт создаёт отдельную папку renders/camera_sweep_ДАТА,
сохраняет входную сцену и диапазоны, рендерит, запускает CLI и собирает CSV.
Исходная scene.json и состояние панели не меняются. Все диапазоны образуют
декартово произведение: число кадров перемножается.

Проверить диапазоны и сохранить только входные JSON без рендера:

```bash
bash 3d_scene/run_camera_sweep.sh --prepare-only
```

Необязательный последний аргумент — новая папка результата (существующая
папка не перезаписывается). SOURCE_SCENE задаёт другую исходную сцену;
PIXI_MANIFEST — другое окружение Pixi (по умолчанию $HOME/pixi.toml).
WIDTH, SAMPLES, BOARD_DISTANCE_M, VARIANT также можно передавать переменными.
Для подготовленного примера полный последующий запуск экспортёра:

```bash
pixi run --manifest-path "$HOME/pixi.toml" python 3d_scene/scene_export.py \
  --scene 3d_scene/renders/camera_sweep_prepared_example/input_scene.json \
  --sweep 3d_scene/renders/camera_sweep_prepared_example/input_sweep.json \
  --out 3d_scene/renders/camera_sweep_prepared_example \
  --width 1920 --samples 64 --variant cuda_ad_rgb --board-mode emissive
```

После него отдельно запустите run_calibmar.sh и collect_calibmar_results.py
с той же папкой набора, как описано выше.

Читаемый конфиг стекла для calibmar

Экспортёр пишет `housing.inner_radius_m` — радиус внутренней поверхности,
`housing.layers` — список слоёв от внутреннего к внешнему, каждый с thickness_m
и refractive_index. Среды до/после стекла — inside_refractive_index и
outside_refractive_index. Внешний радиус равен внутреннему плюс толщина слоя.
Сейчас рендерер и решатель поддерживают один слой (две границы); несколько
слоёв CLI отклоняет явно, их физика ещё не реализована.
Начальное приближение вынесено в initialization: необязательный стартовый
центр dome_center_camera_opencv_m и флаг estimate_dome_offset. Экспортёр
записывает центр купола относительно ОПОРНОЙ камеры без её неизвестного люфта
и устанавливает estimate_dome_offset=false, чтобы автоматическая оценка CLI
не заменила этот старт. Это номинальное приближение в метрах по осям OpenCV,
а не истинный центр относительно реальной камеры. Оптимизация затем уточняет
центр и позу доски. При переносе/повороте всей установки относительный старт
сохраняется; при изменении camera_d*/camera_r* старт не следует за истинной
камерой. Для произвольных сцен без опорного узла нужен отдельно заданный старт.
Сам CLI по-прежнему допускает отсутствие initialization (нулевой центр и
автооценка); экспортёр теперь использует известную геометрию опорной камеры.
Старые конфиги-массивы CLI продолжает читать.

Для больших наборов можно сохранять overlay в исходном разрешении и не
дублировать исходник в image_upsampled.png:

```bash
UPSAMPLE=1 KEEP_UPSAMPLED=0 bash 3d_scene/run_camera_sweep.sh
```

Исходные image.png, overlay и числовые отчёты остаются. После рендера скрипт
пытается обработать имеющиеся кадры и собрать CSV даже при сбое части рендеров;
коды этапов сохраняются в pipeline_status.txt.
